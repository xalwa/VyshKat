# ВышКат

Консольное приложение учёта имущества кикшеринга на Kotlin/JVM.
Транспорт поступает в парк после техосмотра; вещи учитываются отдельно.
Программа выводит инвентарный список, количество транспорта и вещей,
суточное потребление энергии и транспорт, подходящий новичкам.

## Требования и запуск

- JDK 21. `JAVA_HOME` должен указывать на каталог JDK, а не на его папку `bin`.
- Интернет при первом запуске для загрузки Gradle и библиотек.
- Gradle отдельно устанавливать не требуется: в проект включён Gradle Wrapper 9.6.0.

Все команды ниже выполняются из папки проекта `vyshkat`, где находится `gradlew`.
На машине разработки JDK 21 установлен в `~/.jdks/ms-21.0.12.1`:

```bash
export JAVA_HOME="$HOME/.jdks/ms-21.0.12.1"
export PATH="$JAVA_HOME/bin:$PATH"
java -version
```

На другом компьютере нужно подставить путь к своей установке JDK 21.

Запуск демонстрации:

```bash
./gradlew run
```

Приложение автоматически выполняет подготовленный сценарий и завершается.
Ручной ввод для запуска демонстрации не нужен. Все данные хранятся в памяти
и создаются заново при следующем запуске.

Сборка приложения и запуск тестов:

```bash
./gradlew build
```

Только тесты:

```bash
./gradlew test
```

Проверка с чистого состояния и формирование отчётов покрытия:

```bash
./gradlew clean build koverHtmlReport koverXmlReport
```

`clean` удаляет результаты предыдущей сборки из `build`. Остальные задачи
заново компилируют приложение, выполняют тесты и создают отчёты.

Для Windows предусмотрен `gradlew.bat`: например, `gradlew.bat test`.

## Демонстрация работы

Сценарий находится в `runDemo` в [Main.kt](src/main/kotlin/Main.kt):

1. Создание самоката и проверка пригодности для новичка.
2. Техосмотр исправного самоката, затем изменение его состояния на неисправное.
3. Отказ при попытке принять неисправный самокат `S-001`.
4. Успешная приёмка велосипеда `B-001` с простотой 5.
5. Учёт шлема `H-001` и зарядной станции `C-001`.
6. Вывод названий и инвентарных номеров принятого имущества.
7. Расчёт энергии: сначала 1.5 кВт·ч за сутки от станции.
8. Успешная приёмка исправного самоката `S-002` с расходом 0.5 кВт·ч за сутки.
9. Отклонение повторного добавления `S-002` и шлема с таким же номером.
10. Итоговые отчёты по составу парка и транспорту для новичков.

Ожидаемые итоговые значения:

```text
После приёмки энергопотребление парка: 2.0 кВт·ч
...
Транспорта в парке: 2
Вещей на балансе: 2
Транспорт для новичков:
S-002: Исправный самокат
```

## Структура и решения модели

```text
src/main/kotlin/
├── Main.kt
├── model/       # Транспорт, вещи и общие договоры
├── service/     # Техосмотр, приёмка, хранение и отчёты
└── di/          # Правила создания служебных объектов в Koin
src/test/kotlin/
└── service/     # Тесты поведения парка и подмена техосмотра
```

- [InventoryItem](src/main/kotlin/model/InventoryItem.kt) задаёт номер и название.
  Его реализуют обе иерархии: `Transport` и `Equipment`.
- [EnergyConsumer](src/main/kotlin/model/EnergyConsumer.kt) задаёт суточный расход
  в кВт·ч. Его реализуют `Scooter` и `ChargingStation`; велосипед и шлем этого
  договора не имеют.
- [Transport](src/main/kotlin/model/Transport.kt) хранит общие свойства транспорта,
  простоту и техническое состояние. Наследники — `Scooter` и `Bicycle`.
- [Equipment](src/main/kotlin/model/Equipment.kt) объединяет вещи на балансе.
  Наследники — `Helmet` и `ChargingStation`.
- [ServiceCenter](src/main/kotlin/service/ServiceCenter.kt) задаёт операцию осмотра.
  [BasicServiceCenter](src/main/kotlin/service/BasicServiceCenter.kt) принимает
  транспорт, у которого `isOperational == true`. Это выбранное упрощённое правило:
  задание не определяет конкретный алгоритм технической диагностики.
- [FleetService](src/main/kotlin/service/FleetService.kt) хранит один приватный
  список `InventoryItem`. Потребление, количества и список новичков вычисляются
  по текущему составу имущества; отдельные изменяемые копии отчётов не хранятся.
- [AdmissionResult](src/main/kotlin/service/AdmissionResult.kt) различает успешное
  добавление, отказ осмотра и повтор инвентарного номера.

Правила учёта:

- Номера и названия не могут быть пустыми или состоять только из пробелов.
- Простота транспорта находится в диапазоне 1–10. Для новичка подходит значение ≥ 6.
- Расход энергии должен быть конечным неотрицательным числом; ноль разрешён.
- Номер уникален среди транспорта и вещей. Уникальность определяется точным
  совпадением строки с учётом регистра.
- При приёмке транспорта сначала проверяется номер, затем проводится техосмотр.
  Отказ не меняет имущество парка.
- Для вещей применяется отдельный `addEquipment`, который проверяет номер.
  Обойти осмотр транспорта через этот метод нельзя: его параметр имеет тип `Equipment`.
- Общая энергия включает все принятые `EnergyConsumer`, в том числе станции.
  Отклонённая техника не участвует в сумме и остальных отчётах.
- Техосмотр выполняется при приёмке. Последующее изменение технического состояния
  само по себе не удаляет уже принятое имущество из учёта.

## SOLID

### S — разделение ответственности

`Main.kt` занимается запуском и консольным выводом. `BasicServiceCenter` принимает
решение об исправности. `FleetService` организует учёт, приёмку и отчёты.
Изменение оформления консоли не требует менять правило техосмотра.

### O — расширение

Новый вид транспорта наследует `Transport`; электрический вид дополнительно
реализует `EnergyConsumer`. `transportCount`, `beginnerVehicles` и
`totalDailyEnergyKwh` работают через общие типы и не перечисляют конкретные модели.
Для показа нового вида потребуется добавить его создание в демонстрацию.

### L — соблюдение договоров наследования

`Scooter` и `Bicycle` сохраняют свойства и поведение `Transport`, включая допустимую
простоту и правило для новичков. `Equipment` и `Transport` предоставляют данные
`InventoryItem`, поэтому одна функция `printItem` работает с обеими иерархиями.
Потребители энергии предоставляют конечный неотрицательный расход.

### I — интерфейсы по отдельным возможностям

`InventoryItem` отделён от `EnergyConsumer`. Шлему не требуется фиктивный расход,
а станции — характеристика пригодности для езды новичка.
**Этот принцип наиболее явно виден в модели.**

### D — зависимость от абстракции

Конструктор `FleetService` принимает интерфейс `ServiceCenter`.
Парк не создаёт `BasicServiceCenter` самостоятельно и не обращается к Koin.
Реализация выбирается в точке сборки приложения или передаётся напрямую в тесте.

### Сознательное ограничение принципов

Граница SRP выбрана достаточно широкой: `FleetService` объединяет хранение в памяти
и отчёты учёта. Для небольшого проекта это связная задача. Выделение отдельного
репозитория и отдельных классов для каждого отчёта увеличило бы число слоёв.
При появлении базы данных хранение можно выделить за отдельную границу.

## DI-контейнер

Используется Koin 4.2.2. Функция [appModule](src/main/kotlin/di/AppModule.kt)
описывает два определения:

```kotlin
single<ServiceCenter> { BasicServiceCenter() }
single { FleetService(get()) }
```

`single` сохраняет экземпляр для повторных запросов, а `get()` получает техосмотр
для конструктора парка. В `main` создаётся локальный контейнер, из него извлекаются
объекты для `runDemo`; в `finally` контейнер закрывается.

`appModule()` создаёт новый объект модуля при каждом вызове, чтобы отдельные
контейнеры получали независимые определения и состояние парка.

## Тесты и покрытие

В [FleetServiceTest](src/test/kotlin/service/FleetServiceTest.kt) находятся пять тестов:

| Тест | Проверяемое поведение |
|---|---|
| `acceptedTransportIsStored` | Одобренный транспорт сохраняется |
| `rejectedTransportIsNotStored` | При отказе парк остаётся пустым |
| `duplicateNumbersDoNotChangeInventory` | Повтор номера в транспорте и вещах отклоняется |
| `energyIncludesStationAndExcludesRejectedTransport` | Станция участвует в энергии, отклонённый самокат — нет |
| `beginnerVehiclesIncludeScoreSixButExcludeFive` | Оценка 6 включается, 5 исключается; вещи не попадают в список |

`FixedServiceCenter` — приватная тестовая подмена с заранее заданным результатом.
Она передаётся через конструктор `FleetService`. В тесте отказа самокат исправен,
но подмена возвращает `false`: это фиксирует соблюдение решения зависимости.
Для вычислений `Double` применяется допуск сравнения.

Для покрытия используется Kover 0.9.8:

```bash
./gradlew koverHtmlReport koverXmlReport
```

Эти задачи запускают необходимые тесты автоматически. Отчёты создаются в:

- HTML: `build/reports/kover/html/index.html`;
- XML: `build/reports/kover/report.xml`;
- результаты JUnit: `build/reports/tests/test/index.html`.

Область измерения: модель, сервисы и настройки DI. Из отчёта явно исключён только
JVM-класс `MainKt`, содержащий консольный запуск, демонстрацию и форматирование вывода.
Остальной исходный код не исключается. Консольная демонстрация проверяется запуском.
Покрытие строк показывает выполнение кода тестами, а не гарантирует отсутствие ошибок.

Ориентир задания — покрытие не менее 60%; фактическое значение нужно смотреть
в отчёте, сформированном для текущих исходников.

Последняя контрольная проверка: **18 октября 2026 года**. Чистая сборка и пять
JUnit-тестов прошли без ошибок и пропусков. Покрытие строк в указанной области —
**81.18% (69 из 85 учитываемых строк)**. `MainKt` исключён, настройки DI остаются
в отчёте. Это результат текущего набора из пяти тестов; при изменении исходников
покрытие нужно измерить заново.

## Что потребуется при расширении

- **Новый транспорт:** добавить наследника `Transport`, при необходимости реализовать
  `EnergyConsumer`. Общие отчёты сохранят работу. Создание нового типа нужно показать
  в консоли; дополнительные особенности осмотра могут потребовать новой реализации
  `ServiceCenter` и изменения определения в `appModule`.
- **Сотрудник:** отдельная модель; по условию сотрудники не являются имуществом.
  Их не следует автоматически добавлять в `InventoryItem` или текущий список парка.
- **Склад запчастей:** отдельные сущности и операции остатков, поступления и списания.
  Для учёта количества одинаковых деталей одной инвентарной модели недостаточно.
  Текущий учёт транспорта и существующие отчёты можно сохранить.

и наследование, уточнялись интерфейсы, добавлялся велосипед и правило для новичков,
классы переносились из общего файла в пакеты `model` и `service`, исправлялись импорты.
Последующая часть кода добавлялась ИИ после обсуждения и согласования шагов.
